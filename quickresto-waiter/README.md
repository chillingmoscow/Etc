# QuickResto Waiter — PoC приложения официанта

Прототип, который доказывает осуществимость архитектуры из плана:
**офлайн-первая PWA (телефон официанта) → BFF (хранит креды QuickResto) → API QuickResto**,
где заказ официанта становится реальным заказом в QuickResto и виден на iPad-терминале.

> Это PoC, а не прод. Цель — «пощупать» весь поток end-to-end и подготовить почву
> для боевой интеграции. Полный план и анализ рисков — в файле плана проекта.

## Что внутри

```
quickresto-waiter/
├── bff/          # backend-for-frontend (Node 18+, без зависимостей)
│   ├── server.mjs       # HTTP-сервер: отдаёт PWA + API (/api/menu, /api/tables, /api/orders, .../status)
│   ├── quickResto.mjs   # клиент QuickResto (MOCK + REAL); buildOrderPayload — единая точка схемы
│   ├── config.mjs       # env/.env; нет кредов → MOCK
│   ├── store.mjs        # in-memory идемпотентность + имитация статусов (в проде → Postgres/Supabase)
│   ├── mockData.mjs     # демо-меню и столы
│   └── .env.example     # шаблон кредов
├── pwa/          # офлайн-первый клиент (vanilla JS, IndexedDB, service worker; без сборки)
│   ├── index.html  styles.css  app.js  db.js  sw.js  manifest.webmanifest  icon.svg
└── spike/        # Фаза 0 — проверка реального API QuickResto
    └── spike.mjs   README.md
```

## Запуск (2 минуты, без кредов — MOCK-режим)

Нужен только **Node.js 18+**. Зависимости ставить НЕ надо.

```bash
cd quickresto-waiter/bff
node server.mjs
# открыть http://localhost:8787
```

Откроется приложение официанта. Можно:
- выбрать **стол**, потыкать **меню**, собрать **заказ**, «Отправить на кухню»;
- увидеть заказ в списке со сменой **статуса** (NEW → COOKING → READY → CLOSED) — это имитация синхронизации статусов из QuickResto;
- выключить сеть (DevTools → Offline) и убедиться, что заказы **встают в очередь** и **досылаются** при возврате сети (офлайн-первая работа);
- установить как PWA (значок «Установить» в адресной строке).

## Боевой режим (когда будут креды)

1. Прогоните **спайк** (Фаза 0) — см. `spike/README.md`. Он подтвердит схему создания заказа и привязку к столу.
2. Скопируйте `bff/.env.example` → `bff/.env`, заполните `QR_LAYER`, `QR_LOGIN`, `QR_PASSWORD`
   (логин/пароль API из бэк-офиса: **Предприятие → Настройки**).
3. При необходимости поправьте по итогам спайка `buildOrderPayload()` в `bff/quickResto.mjs`
   и переменные `QR_*` в `.env` (модуль/класс столов, имя поля привязки к столу).
4. `node server.mjs` — теперь BFF ходит в реальный QuickResto.

> **Безопасность:** креды живут только в `bff/.env` (в гит не коммитится) и никогда не попадают
> в браузер. На клиенте — только сессия приложения. Это намеренно: see план, риск R9.

## Что этот PoC доказывает

- Архитектура **PWA → BFF → QuickResto** рабочая и связная (end-to-end поток заказа).
- **Офлайн-первый** ввод с очередью и досылкой реализуем на дешёвом стеке без зависимостей.
- **Идемпотентность** (ключ на заказ) защищает от дублей при ретраях.
- Точка интеграции с QuickResto **локализована** в одном файле — после спайка её правка минимальна.

## Что НЕ входит в PoC (осознанно)

- Реальная БД/реалтайм (здесь in-memory и поллинг; в проде — Supabase).
- Авторизация официантов, модификаторы/размеры, дозаказ как отдельный поток, админка.
- Подтверждённая схема создания заказа в QuickResto — это результат Фазы 0 (спайк).
